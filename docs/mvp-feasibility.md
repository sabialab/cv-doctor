## 二、技术可行性：非技术用户路径每个环节

### 2.1 环节 1：上传简历

**用户行为：** 从手机/电脑上传一份 Word 或 PDF 简历

**技术方案：**

| 格式 | 方案 | 可行性 | 难点 |
|------|------|--------|------|
| DOCX | python-docx | ✅ 非常成熟 | 表格、图片嵌入解析不完美 |
| PDF (文本型) | PyMuPDF | ✅ 成熟稳定 | 双栏布局、表格解析困难 |
| PDF (扫描型) | OCR (PaddleOCR) | ⚠️ 需额外依赖 | 准确率依赖图片质量 |
| 图片截图 | OCR + Kimi 多模态 | ⚠️ P1 可做 | 成本高、准确率不稳定 |
| 手机拍照 | OCR | ⚠️ P1 可做 | 光线、角度影响大 |

**P0 方案：** 只做 DOCX + 文本型 PDF，覆盖 90%+ 场景。
中国求职者主流用 Word 写简历，PDF 多为 Word 导出的文本型。

**关键风险：**
- 中国简历模板五花八门（双栏、表格、图标、照片），解析会出错
- 很多人简历用 WPS 编辑，格式兼容性需测试
- 部分简历包含表格嵌套，段落关系丢失

**对策：**
- 解析后展示给用户确认，允许手动修正
- 提供"粘贴简历文本"作为降级方案
- 收集解析失败样本，持续优化

### 2.2 环节 2：粘贴 JD

**用户行为：** 从 BOSS 直聘/拉勾/猎聘复制 JD 文本粘贴到输入框

**技术方案：**
- 纯文本输入框，不做任何自动采集
- 支持粘贴富文本（HTML），自动清理格式
- 支持上传 JD 截图（P1，OCR）

**可行性：** ✅ 非常简单，零风险

**用户习惯匹配度：** 高。BOSS 直聘用户习惯复制岗位描述发给朋友讨论。

### 2.3 环节 3：等待分析

**用户行为：** 点击"开始分析"后等待结果

**技术方案：**
- 异步任务：前端 WebSocket / SSE 推送进度
- 后端 Redis 队列 + FastAPI Background Tasks
- 进度条：解析中 → 分析中 → 生成建议中

**等待时间估算：**

| 模式 | 步骤数 | 预计时间 | 用户感受 |
|------|--------|----------|----------|
| Quick Mode | 5 次 LLM 调用 | 30-60 秒 | 可接受 |
| Target Mode | 8 次 LLM 调用 | 1-3 分钟 | 需要进度条 |

**关键风险：**
- DeepSeek API 偶尔响应慢（高峰期 10-30 秒/次）
- 网络抖动导致超时

**对策：**
- 超时重试（3 次）
- 降级：如果 DeepSeek 不可用，切 Kimi K2.5（更便宜）
- 进度条让用户知道"还在工作"

### 2.4 环节 4：查看诊断结果

**用户行为：** 看 Match Score、差距分析、修改建议

**UI 设计要点（非技术用户）：**

```
┌─────────────────────────────────────────┐
│  📊 匹配度：72/100                       │
│  ████████████████░░░░░  72%             │
│                                          │
│  ✅ 你已匹配的能力 (5项)                  │
│  Go 语言 · MySQL · 微服务 · RESTful · Git │
│                                          │
│  ⚠️ 可以优化的地方 (2项)                  │
│  K8s → 你有 Docker 经验，可以更突出       │
│  分布式 → 你有相关概念，可以更具体         │
│                                          │
│  ❌ 建议补充的能力 (1项)                   │
│  Rust → 你目前没有相关经验，建议如实       │
└─────────────────────────────────────────┘
```

**非技术用户的关键需求：**
- 不要看技术术语，要看"我能做什么"
- 用 ✅⚠️❌ 而不是 "full/partial/missing"
- 用进度条/颜色而不是数字表格
- 每条建议要有"为什么"

### 2.5 环节 5：审阅修改建议

**用户行为：** 逐条看修改建议，接受/拒绝/编辑

**UI 设计要点：**

```
┌─────────────────────────────────────────┐
│  建议修改 1/7                            │
│                                          │
│  📍 来源：JD 第 3 条要求                  │
│  "熟悉 Go 语言，有微服务架构经验"         │
│                                          │
│  原文：                                   │
│  熟悉 Go 语言，参与过微服务项目开发        │
│                                          │
│  建议改为：                               │
│  熟练掌握 Go 语言，有微服务架构设计与      │
│  落地经验，参与过 XX 项目核心模块开发      │
│                                          │
│  💡 为什么这样改：                        │
│  JD 强调"架构经验"而非"参与"，用"熟练      │
│  掌握"替代"熟悉"更匹配岗位要求。           │
│                                          │
│  ⚡ 风险：低风险，只改了表述               │
│                                          │
│  [✅ 接受]  [❌ 拒绝]  [✏️ 编辑]          │
└─────────────────────────────────────────┘
```

**非技术用户的关键需求：**
- 用大按钮，不要用小链接
- "为什么这样改"要用大白话
- 风险用颜色标注（绿/黄/红）
- 支持"全部接受"一键操作
- 支持手动编辑（内联编辑器）

### 2.6 环节 6：导出简历

**用户行为：** 下载优化后的简历（DOCX/PDF）

**技术方案：**

| 格式 | 方案 | 可行性 |
|------|------|--------|
| DOCX | python-docx 模板填充 | ✅ 成熟，用户可继续用 Word 编辑 |
| PDF | WeasyPrint (HTML→PDF) | ⚠️ 中文字体需预装，Docker 环境需配置 |
| Markdown | 直接生成 | ✅ 但非技术用户不用 |

**P0 方案：** DOCX 优先（用户最熟悉），PDF 做基础版。

**关键风险：**
- DOCX 模板和用户原始简历格式差异大
- 中文字体在不同系统显示不一致
- PDF 分页、表格渲染问题

**对策：**
- 尽量保留用户原始简历的格式结构
- 使用系统默认中文字体（微软雅黑/苹方/思源黑体）
- DOCX 让用户自己在 Word 里微调

## 三、前端技术方案

### 3.1 推荐方案：Next.js + Tailwind + shadcn/ui

| 组件 | 方案 | 理由 |
|------|------|------|
| 框架 | Next.js 15 (App Router) | SSR、API Routes、老大的强项 |
| UI 库 | shadcn/ui + Tailwind | 现代、可定制、中文友好 |
| 文件上传 | react-dropzone | 拖拽 + 点击上传 |
| Diff 审阅 | 自定义组件 | 核心差异化，必须精细设计 |
| 进度推送 | Server-Sent Events | 比 WebSocket 简单 |
| 导出 | 后端生成，前端下载 | 简单可靠 |

### 3.2 移动端适配

**必须做响应式：** 70%+ 用户会从手机访问。

- 上传：支持手机文件选择 + 相册拍照（P1）
- 粘贴 JD：大文本框，支持粘贴
- 审阅：卡片式布局，左右滑动切换
- 导出：下载到手机，分享到微信

## 四、后端技术方案

### 4.1 API 设计

```
POST /api/upload-resume     → 解析简历，返回 Resume 结构
POST /api/analyze-jd        → 分析 JD，返回 JobAnalysis
POST /api/quick-diagnose    → Quick Mode 一键诊断
POST /api/target-diagnose   → Target Mode（含公司分析）
GET  /api/diagnose/:id      → 获取诊断结果
POST /api/review-change     → 接受/拒绝/编辑单条修改
POST /api/export            → 导出 DOCX/PDF
DELETE /api/data/:id        → 一键删除用户数据
```

### 4.2 异步任务流

```
用户上传 → 解析(同步) → LLM分析(异步) → 推送进度 → 返回结果
                      ↓
               Redis Queue + Worker
               DeepSeek V4 Flash
               Kimi K2.6 (Target Mode)
```

### 4.3 文件存储

```
上传文件 → 临时存储(24h自动删除)
导出文件 → 临时存储(下载后可删除)
用户数据 → PostgreSQL(元数据)
         → 不存储原始简历文本（除非用户选择）
```

## 六、竞品对比（修正版）

### 6.1 国内竞品图谱

**直接竞品（Web 简历工具）：**
- **超级简历 WonderCV**（3000万+用户）：AI评分+JD关键词优化+模板库，但不做diff审阅和证据链
- **简历AI (easycv.cn)**：AI润色+一键专业表达，但不做JD匹配度分析
- **知页简历**：高颜值模板+优化建议，但AI能力弱
- **智联/拉勾/BOSS自带诊断**：平台内免费评分，但只能用于自家平台

**间接竞品（CLI/开源）：**
- **Career-Ops**（48.1k★）：10维度JD评估+定制简历+批量扫描，但CLI非Web
- **JadeAI**（1.7k★）：全能简历生成器，但不是优化器

**最大隐性竞品：**
- **免费 Prompt 方案**（Kimi/DeepSeek + 结构化Prompt）：零成本零门槛，但输出是黑盒

### 6.3 竞争对策

| 威胁 | 对策 |
|------|------|
| 超级简历已有"评分+JD优化" | 不打"AI简历优化"标签，打"简历手术台"；突出diff审阅 |

### 6.4 首页文案策略（避免和超级简历撞车）

**不要写：**
- "AI简历优化"（和超级简历撞车）
- "一键生成简历"（那是生成器）
- "ATS通过率100%"（不可信）

**要写：**
- "简历手术台：每处修改都有证据"
- "不编经历，只改表达"
- "上传简历 + 粘贴JD = 可审计的修改报告"
- "比直接问AI更可信、更可控"

## 九、风险清单（非技术用户视角）

| 风险 | 等级 | 影响 | 对策 |
|------|------|------|------|
| PDF 解析失败 | **高** | 用户上传简历后看到乱码 | 提供"粘贴文本"降级方案；解析后让用户确认 |
| LLM 输出不可控 | **高** | 修改建议离谱或编造事实 | Policy Guard + 证据链 + diff 审阅 |
| 等待时间过长 | **中** | 用户等 2 分钟没耐心 | 进度条 + 预计时间 + 免费试用快速出结果 |
| 移动端体验差 | **中** | 手机用户占比高 | P0 就做响应式，优先移动端 |
| DOCX 格式丢失 | **中** | 导出的简历和原始格式差异大 | 尽量保留原始结构；让用户在 Word 里微调 |
| 用户不知道粘贴什么 | **中** | 不知道什么是 JD | 提供示例 + "从 BOSS 直聘复制岗位描述" |
| 付费转化低 | **中** | 用户用完免费额度就走 | 免费给 3 条建议 + Match Score；完整版付费 |
| API 限流 | **低** | 高并发时 DeepSeek 限流 | 重试 + 降级到 Kimi K2.5 |

## 十、结论

### 10.1 P0 MVP 可行性：✅ 高度可行

- LLM 成本极低（¥0.03/次），定价完全由用户价值决定
- 技术栈成熟（Next.js + FastAPI + Pydantic + python-docx）
- 开发工作量可控（~4 周）
- 部署成本极低（Vercel + 已有 VPS）
- 国内无直接竞品做"可审计修改 + 公司分析"

### 10.2 最大风险

1. **PDF 解析质量** — 中国简历模板五花八门，解析会出错
   → 对策：DOCX 优先 + 粘贴降级 + 用户确认

2. **LLM 输出质量** — 非技术用户看不懂或觉得不靠谱
   → 对策：大白话 + ✅⚠️❌ + 证据链 + diff 审阅

3. **付费意愿** — 用户觉得"ChatGPT 免费能做"
   → 对策：差异化在"可审计修改"，不是"AI 改简历"

### 10.3 建议的 P0 最小闭环

```
用户上传 DOCX → 粘贴 JD → 等待 30 秒 →
看到 Match Score + 3-5 条修改建议 →
逐条接受/拒绝 → 下载 DOCX
```

这就是最小可行产品。先验证这个闭环，再加 Target Mode。
